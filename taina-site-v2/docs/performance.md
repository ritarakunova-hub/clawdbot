# Производительность — отчёт (Этап 12)

Простыми словами: сколько сейчас весит сайт и что грузится сразу, а что —
только по мере скролла. Первый формальный замер (готовых цифр «было» из
более ранних этапов нет — раньше это отдельно не измерялось).

## Что грузится сразу (до первого взаимодействия)

Реально блокирующий JS — это только маленькие «загрузочные» скрипты
каждой секции (они лишь вызывают `import()` для своей 3D-сцены, сам код
сцены не включён в них):

| Файл | Вес (gzip) |
|---|---|
| Hero.astro (скрипт) | 1,0 КБ |
| Territories.astro (скрипт) | 1,1 КБ |
| Proyavka.astro (скрипт) | 0,5 КБ |
| Project.astro (скрипт) | 0,5 КБ |
| Behemoth.astro (скрипт) | 0,6 КБ |
| Packages.astro (скрипт) | 0,7 КБ |
| Footer.astro / Layout.astro (скрипты) | < 0,5 КБ каждый |
| **Итого** | **≈ 5 КБ** |

CSS — один файл, **8,2 КБ** (gzip). Это и есть «стартовый JS/CSS» в
смысле бюджета CLAUDE.md (≤ 250 КБ gzip) — фактически **≈ 13 КБ**,
с большим запасом.

## Что грузится лениво (после первого экрана)

Каждая 3D-сцена (`hero`, `proyavka`, `project`, `behemoth`) подгружает
свой код через `import()` только после `window.load` — то есть уже после
первой отрисовки страницы, не блокируя её. Самый тяжёлый общий кусок —
`postFx.js` (общий для всех сцен EffectComposer/UnrealBloomPass/Three.js) —
**110 КБ gzip**, плюс код каждой сцены отдельно (0,5–6 КБ gzip каждая).
Итого лениво догружаемого 3D-кода — **≈ 120 КБ gzip**, уже после того,
как страница показана и с ней можно взаимодействовать.

Это соответствует требованию CLAUDE.md «3D-код и ассеты подгружаются
лениво после первого экрана» — здесь это буквально «сразу после
загрузки, но не блокируя её», а не «только когда доскроллили» (так было
решено ещё на более ранних этапах — соседняя сцена всегда готова
заранее, чтобы переход между ними был без мерцания, см. комментарии в
`Proyavka.astro`).

## Шрифты

Self-host через `@fontsource`, только кириллица + латиница (не полный
юникод-набор) — Cormorant Garamond 500 и Inter 400/500/600. Суммарно
**136 КБ** во всех начертаниях, но браузер грузит только то, что реально
используется на экране (`font-display: swap` + метрики через
`fontaine`, чтобы не прыгал layout при подмене шрифта). Преднагрузка
(`<link rel="preload">` в `Layout.astro`) — только 4 файла, необходимых
для самого первого экрана (Inter 400, Cormorant 500, обе кириллица).

## Lighthouse — почему не прогнала полноценно

Эта сессия работает в песочнице без настоящего GPU: WebGL2 рендерится
через SwiftShader (программный рендер), который заметно медленнее
реального железа (это уже задокументировано и проверено на более ранних
этапах — например, тест `quality-dpr.spec.ts` учитывает это через
щедрые таймауты). Формальный Lighthouse-прогон на мобильном профиле в
такой среде показал бы заниженный (нерепрезентативный) показатель
именно из-за 3D-сцен — не потому что код медленный, а потому что
песочница не может отрисовать WebGL быстро в принципе.

**Что можно измерить честно прямо сейчас (и измерено выше):** вес
бандлов, CSS, шрифтов, порядок и лень загрузки — это не зависит от GPU.
**Что нужно измерить на реальном железе** (см. финальный список
блокеров в конце работы): Lighthouse performance-score на мобильном
профиле, реальные LCP/INP/CLS на живом сайте после деплоя на Netlify
(Этап 15) — их корректно снимать только там, не в этой песочнице.

## Итог

Бюджет «стартовый JS ≤ 250 КБ gzip» соблюдён с большим запасом (реально
≈ 13 КБ). 3D-код лениво догружается после первого экрана, не блокируя
его. Числа LCP/CLS/Lighthouse-score с реального мобильного устройства и
после деплоя — в списке того, что нужно снять на настоящем железе после
выхода в интернет (Этап 15).
