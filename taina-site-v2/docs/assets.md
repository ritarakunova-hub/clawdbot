## Почему нет скрипта AVIF/WebP/srcset

PROMPTS.md (Этап 11) просит скрипт оптимизации под несколько форматов и
ширин экрана — это оправдано, когда на странице десятки фотографий или
хотя бы одна крупная героическая картинка. Здесь: одно фото 23 КБ уже
меньше, чем весил бы один WebP-вариант с нормальным качеством, и оно не
показывается как `<img>` (это WebGL-текстура, грузится через
`THREE.TextureLoader`, а не через `<img srcset>` — механизм оптимизации
для тега `<img>` тут физически неприменим). Строить пайплайн
AVIF/WebP/srcset под один файл — это добавлять сложность без пользы, а
CLAUDE.md прямо просит не добавлять зависимости без причины.

**Правило на будущее:** как только на странице появится «Образы»/портрет
как настоящее `<img>` или видеопетля — до этого момента отдельный скрипт
не нужен, а как только появится, добавить `sharp`-скрипт (уже есть в
зависимостях транзитивно через Astro) с генерацией AVIF+WebP+srcset под
360/768/1440 и запасной кадр для уровня B/C — сам подход описан в
PROMPTS.md, менять не нужно, просто ещё не наступил повод.

## 3D-ассеты (glTF/Draco/KTX2)

Все три 3D-сцены («Хиро», «Проявка», «Проект», «Бегемот») построены на
процедурной геометрии Three.js (`PlaneGeometry`, `BufferGeometry` с
руками заданными вершинами для ромба, `InstancedBufferGeometry` для
листов) — ни одного `.gltf`/`.glb`-файла в проекте нет.

**Правило, которое просит зафиксировать PROMPTS.md:** пока сцены на
процедурной геометрии — glTF/Draco/KTX2 не нужны. Если в сцену добавится
готовая 3D-модель (не процедурная форма) — заводить её через glTF с
Draco-сжатием геометрии и KTX2-текстурами, не через необработанный
`.glb` с PNG-текстурами внутри — это и есть весь бюджет 3–4 МБ на
3D-ассеты из CLAUDE.md.
