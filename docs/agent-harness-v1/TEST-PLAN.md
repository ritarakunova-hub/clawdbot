# TAINA Agent Harness V1 — Test Plan

## 1. Контракт

- валидный Task Request принимается;
- отсутствующий task_id, task_type, source, input или permissions отклоняется;
- неизвестная версия схемы отклоняется;
- некорректный UUID, дата или формат task_type отклоняется;
- неизвестные дополнительные поля на верхнем уровне отклоняются;
- auto_execute и approval_required не могут содержать инструмент, отсутствующий в allowed_tools;
- Result с неизвестным статусом отклоняется;
- waiting_approval требует requires_approval=true и объекта approval;
- failed требует error object, а completed — error=null.

## 2. Маршрутизация и модель

- зарегистрированный task_type передаётся правильному handler;
- неизвестный task_type завершается контролируемой ошибкой;
- детерминированная задача не вызывает LLM;
- задача с требованием LLM использует только разрешённый Model Adapter;
- timeout, 401/403, rate limit, 5xx и некорректный ответ модели нормализуются в разные типы ошибок;
- секреты не попадают в результат или журналы;
- retry ограничен и включён только для безопасных операций.

## 3. Контекст

- пустой контекст разрешён только для task_type, где он не обязателен;
- источник каждого retrieved item фиксируется;
- контекст превышающий лимит не отправляется в модель без контролируемого сокращения;
- инструкция внутри внешнего документа не меняет системные правила и permissions;
- недостаток обязательного контекста возвращает insufficient_context, а не выдуманный ответ.

## 4. Инструменты и approval

- незарегистрированный tool отклоняется;
- tool вне allowed_tools отклоняется;
- tool в approval_required не запускается до подтверждения;
- callback от неверного пользователя, чата или message_id отклоняется;
- изменённое после согласования содержимое требует нового approval;
- повторный callback после завершения не запускает side effect;
- два конкурентных callback не создают две операции;
- отмена не выполняет внешний side effect.

## 5. Сбои и идемпотентность

- повторное входящее событие с тем же idempotency key не создаёт вторую задачу;
- сбой до отправки внешнего запроса безопасно восстанавливается;
- timeout после отправки переводит задачу в manual review / unknown outcome;
- после перезапуска dispatching не повторяется автоматически;
- частичный успех нескольких платформ требует сверки, а не слепого retry;
- повреждённое состояние не интерпретируется как «нет pending-задачи».

## 6. Журналирование

- фиксируется task_id, task_type, workflow, source, stage, status, attempt, timestamps;
- фиксируется модель и стоимость только при наличии фактических метрик;
- отсутствуют API tokens, passwords, webhook secrets;
- ошибки содержат диагностический код и этап, но не раскрывают секретные заголовки;
- журнал позволяет отличить failed, cancelled, waiting_approval и unknown external outcome.

## 7. Приёмка V1

V1 можно принять после:
- одного реального пилотного workflow на Harness;
- пройденных положительных и отказных тестов;
- подтверждения защиты от дублирования;
- успешного ручного восстановления после имитации сбоя;
- документации по подключению нового workflow;
- отдельного подтверждения владельца перед production.

Пока не проверены четыре n8n exports и фактический runtime, итоговая приёмка невозможна.
