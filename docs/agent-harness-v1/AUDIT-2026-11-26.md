# Предварительный технический аудит TAINA message automation

**Дата:** 2026-11-26  
**Область:** код, доступный в GitHub PR #6 и PR #7 репозитория ritarakunova-hub/clawdbot.  
**Статус:** preliminary — это аудит исходного кода веток, не production-аудит.

## 1. Проверенные реализации

### PR #6 — прямое размещение в VK и Telegram

Источник: [PR #6](https://github.com/ritarakunova-hub/clawdbot/pull/6), ветка feat/content-autopilot-safe-approval.

Изучены, в частности:
- content-autopilot/index.js;
- content-autopilot/src/pending.js;
- content-autopilot/src/security.js;
- content-autopilot/src/publisher.js;
- content-autopilot/src/telegram.js;
- content-autopilot/test/run.js;
- content-autopilot/README.md.

Наблюдения:
- публикация в VK и Telegram запускается только после явного callback-подтверждения;
- проверяется отдельный TELEGRAM_APPROVER_ID, исходный чат и ID Telegram-сообщения, к которому привязана кнопка;
- состояние перед внешней публикацией переводится в publishing;
- после неоднозначного исхода / перезапуска предусмотрен needs_review, автоматический слепой retry не выполняется;
- состояние записывается атомарной заменой файла; каталог и файл получают ограниченные права;
- Telegram API вызовы имеют 15-секундный timeout;
- есть preflight и тесты безопасности.

Эта реализация содержит полезные защитные паттерны для Harness. Но её capability «публиковать непосредственно в социальные каналы» должна оставаться отдельной и выключенной по умолчанию.

Наблюдения:

- VK- и Telegram-токены в этой реализации не нужны, сервис не публикует непосредственно в каналы;
- есть проверки календаря, защита webhook, защищённый ручной endpoint, readiness endpoint и тесты;
- хранение состояния — JSON-файл; документация требует одну реплику и постоянное хранилище;

## 2. Существенные различия

| Свойство | PR #6 | PR #7 |
|---|---|---|
| Внешний эффект | Прямая публикация в VK и Telegram | Отправка готового текста владельцу |
| Требуемые права | Telegram bot + права публикации VK/Telegram | Telegram bot для личных сообщений |
| Подтверждение | Да | Да |
| Проверка личности | Approver ID + чат + точное сообщение | Пользователь и личный чат |
| Статус перед внешним действием | publishing перед публикацией | approved_for_smmplanner записывается после отправки handoff |
| Риск дублирования при аварии | Уменьшен фиксацией состояния до side effect; остаётся неоднозначность внешнего API | Есть окно между успешной отправкой handoff и сохранением статуса |
| Прямые публикации | Да | Нет |

## 3. Найденные риски и рекомендации

### A-01 — повторная передача handoff после аварии (PR #7)

В resolveApprove сначала вызывается sendSmmplannerReadyMessage, а затем записывается статус approved_for_smmplanner.

Если Telegram принял сообщение, но процесс завершился до сохранения нового статуса, в файле может остаться pending. Повторное нажатие старой кнопки потенциально отправит handoff ещё раз.

**Рекомендация:** перед отправкой сохранять состояние вроде handoff_in_progress с неизменным operation/idempotency key. После успешного ответа записывать approved_for_smmplanner. После неоднозначного timeout/crash переводить задачу в needs_review; автоматически повторять side effect нельзя.

### A-02 — callback не привязан к конкретному сообщению (PR #7)

isTelegramOwnerCallback проверяет личный чат и отправителя, но в изученной реализации не сравнивает callback.message.message_id с сохранённым ID исходного черновика. PR #6 использует более строгую привязку к ID сообщения.

**Рекомендация:** сохранить chat ID + message ID черновика и проверять оба значения перед разрешением callback. Дополнительно валидировать действие и ID задачи.

### A-03 — очистка состояния при неоднозначной отправке черновика (PR #7)

В checkAndSchedule запись pending создаётся до отправки черновика, но при ошибке отправки состояние очищается. Если внешний API принял сообщение, а ответ не дошёл до приложения, следующий запуск может создать второй черновик.

**Рекомендация:** использовать промежуточный статус creating_draft; при неоднозначном исходе сохранять состояние needs_review, а не очищать его.

### A-04 — у Telegram fetch в PR #7 не виден явный timeout

В изученном src/telegram.js вызов fetch не задаёт AbortSignal.timeout. В PR #6 timeout явно предусмотрен.

**Рекомендация:** задавать ограниченный timeout на каждый внешний HTTP-вызов и различать сетевую ошибку, отказ API и неоднозначный результат после отправки.

### A-05 — состояние JSON рассчитано на одну реплику

PR #7 документирует ограничение одной реплики. In-memory Set для защиты от одновременной обработки не является распределённой блокировкой.

**Рекомендация:** в V1 сохранять single-instance deployment как явное ограничение. Перед масштабированием на несколько реплик потребуется атомарный claim/lock в общем хранилище.

### A-06 — два варианта согласования имеют разные модели полномочий

PR #6 допускает прямую публикацию; PR #7 только handoff владельцу. Разрешения нельзя выводить из текста промпта или общего флага send_message.

**Рекомендация:** отдельные tool capabilities, например telegram.owner_draft.send, smmplanner.copy_handoff.send, social.publish.direct. Последнее capability выключено в стандартной конфигурации V1 и требует отдельного явного разрешения.

## 4. Архитектурные факты и пробелы

Подтверждено по коду:
- message automation в доступных ветках реализована как отдельный Node.js/Express-сервис с cron, а не как четыре проверенных n8n workflow;
- в PR #6 и #7 не обнаружен единый GigaChat adapter;
- PR #7 не вызывает LLM в изученном цикле расписания, подготовки черновика и передачи текста;
- PR #7 требует persistent disk и одну реплику.

Не подтверждено:
- какие из веток/PR реально развернуты;
- какой вариант является текущим production-сценарием;
- где физически запущен сервис и какое хранилище подключено;
- являются ли четыре n8n workflow источником событий, отдельными прикладными сценариями или частью другой автоматизации;
- как устроены их credentials, retries и связи;
- используются ли GigaChat и embeddings в этих конкретных сценариях.

## 5. Предварительное заключение

Для безопасной первой интеграции Harness разумно использовать PR #7 как кандидат на базовый сценарий подготовки и согласования контента, а PR #6 рассматривать как отдельный пример более рискованного инструмента прямой публикации.

Это предварительная рекомендация по коду, а не утверждение, что PR #7 уже принят, запущен или соответствует текущему production-процессу.

До окончательного архитектурного решения нужны четыре экспорта n8n и сведения о фактически развернутом варианте сервиса.

## 7. Дополнительная инвентаризация репозитория

Проверены деревья файлов веток `claude/greeting-fhvuma`, `feat/taina-smm-manual-publishing`, `feat/mini-crm-secure-intake` и `security/sales-engine-2026-11-15`. В просмотренных деревьях не обнаружены экспорты n8n workflow (`.json` workflow definitions или файлы с явной структурой n8n). Это не доказывает, что n8n не используется где-либо ещё; только означает, что его конфигурация не находится в проверенных деревьях данного репозитория.

В репозитории есть как минимум три отдельные Node.js/Express-службы:

| Сервис | Основной поток | Модель / оркестрация | Состояние / внешние действия |
|---|---|---|---|
| Content Autopilot PR #7 | Контент-календарь → Telegram draft → owner approval → SMMplanner handoff | Node.js + cron; LLM не требуется для расписания/hand-off | JSON pending state; Telegram message; ручное размещение в SMMplanner |
| mini-CRM | Подписанный Netlify webhook → проверка согласия/дедупликация → Google Sheets → Telegram notification | Node.js + Express; без LLM в intake path | Submission ID и notification status в Google Sheets; сериализация в одном процессе |
| Sales Engine | Поиск компаний → Claude analysis → deterministic scoring → Google Sheets → Telegram review card → ручное копирование сообщения | Node.js + Express + node-cron; Claude/Anthropic, не GigaChat в просмотренной ветке | Google Sheets, Telegram approval; follow-up готовится автоматически, отправка остаётся ручной |

### A-07 — заявленный стек TAINA не совпадает с найденными сервисами

Техническое задание рассматривает n8n Self Hosted и GigaChat как текущую инфраструктуру. Однако просмотренная документация Sales Engine прямо описывает отдельный Node.js-сервис с Claude/Anthropic и Google Sheets; Content Autopilot и mini-CRM также являются отдельными Node.js-сервисами.

**Рекомендация:** не навязывать всем существующим сервисам n8n/GigaChat. До получения четырёх реальных n8n exports подтвердить, какие задачи выполняет n8n, какие сервисы являются действующими, и где именно реально вызывается GigaChat. В Harness Host Adapter должен абстрагировать среду исполнения, а Model Adapter — провайдера модели.

### A-08 — orphaned Telegram review cards (Sales Engine)

В просмотренном `sales-engine/src/pipeline.js` лид сначала записывается в Google Sheets, затем отправляется Telegram review card. Если Telegram send завершится ошибкой, лид остаётся сохранённым, но статус уведомления/карточки не записывается. Карточка может не появиться, а повторный поиск пропустит лида как уже существующего.

В `sales-engine/src/followup.js` follow-up текст и статус `Готов к проверке` записываются в таблицу до отправки Telegram card. При ошибке отправки запись уже изменилась, а автоматический повтор не предусмотрен.

**Рекомендация:** добавить для Sales Engine отдельное состояние delivery, например `draft_delivery_pending / draft_delivery_sending / delivered / needs_review`, с operation key и ручной сверкой при неизвестном исходе. Не переписывать поток до отдельного согласования.

### A-09 — callback привязан к пользователю и чату, но не к точной карточке (Sales Engine)

В просмотренном `sales-engine/src/security.js` `verifyTelegramCallback` проверяет admin user ID и chat ID, но не сверяет Telegram `message_id` с ID сохранённой исходной карточки лида.

**Рекомендация:** при создании карточки сохранить Telegram `message_id` и проверять его вместе с lead ID перед изменением статуса. Этот паттерн уже реализован в текущем PR #10 для Content Autopilot.

### A-10 — mini-CRM зависит от one-instance гарантий

mini-CRM использует in-memory serial queue, а дедупликация строится через последовательность lookup → append в Google Sheets. README требует одну реплику. Это хороший V1-компромисс, но не распределённая атомарность.

Кроме того, код mini-CRM и тесты показывают, что Telegram-уведомление не включает контактные поля и текст запроса. В README есть устаревшая фраза про «контакт» в уведомлении — документацию следует синхронизировать с фактическим поведением кода до включения формы.

**Рекомендация:** сохранить one-instance требование, проверить persistent storage/backup и исправить несогласованную формулировку README при отдельном изменении mini-CRM.

## 8. Обновлённое архитектурное заключение

На основании доступного кода уже видны повторяемые технические потребности для Harness:
- входная валидация и нормализация;
- надёжное управление состояниями;
- дедупликация и idempotency;
- явная идентификация утверждающего пользователя и объекта согласования;
- таймауты и классификация неоднозначного исхода;
- безопасное журналирование;
- capability-based permissions;
- единые контракты для разных Node.js-сервисов и будущего n8n adapter.

Однако нельзя утверждать, что все эти сервисы уже должны быть подключены к Harness. Сначала нужно подтвердить production-статус каждого и получить четыре n8n workflow exports. Отдельные мини-CRM и Sales Engine требуют самостоятельной бизнес- и privacy-приёмки.
