# TAINA Agent Harness V1 — Architecture

## 1. Архитектурная позиция

Harness — это контрольный слой, а не автономный агент. Он управляет жизненным циклом задачи и обеспечивает одинаковые правила валидации, контекста, моделей, инструментов, подтверждений и журнала.

Прикладной workflow остаётся владельцем бизнес-процесса. Harness не должен знать, как именно устроены редакционный календарь, CRM или Knowledge Map.

## 2. Логическая схема

~~~text
Event Source
    |
    v
Host Adapter (n8n / Node service / future adapter)
    |
    v
Task Validator + Normalizer
    |
    v
Task Router -----> Task Registry / Policy
    |
    +----> Context Manager (only when required)
    |
    +----> Model Adapter (GigaChat in V1, only for LLM tasks)
    |
    +----> Tool Gateway (capability + permission check)
                    |
                    v
             Approval Manager
                    |
                    v
              External Tool
    |
    v
Quality Gate
    |
    v
Result Contract
    |
    v
State + Audit Log
~~~

Качество и безопасность — обязательные контрольные границы вокруг прикладного выполнения, а не отдельная «модель-судья», которая заменяет проверяемые правила.

## 3. Модули и ответственность

### Host Adapter
Принимает событие от n8n, Node.js или другого поддержанного оркестратора и преобразует его в Task Envelope. Не содержит бизнес-правил продукта.

**Текущий факт:** четыре n8n source exports и Apps Script найдены и статически проверены; сами exports находятся в состоянии `active: false`. Это подтверждает структуру исходников, но не импорт, deployment или production use.

**V1:** Host Adapter и runtime boundary выбираются после сверки live n8n version/workflow IDs/credentials и фактически работающего message service. До этой проверки не переносить orchestration из существующей системы и не предполагать, что исходные exports совпадают с live runtime.

### Task Validator + Normalizer
Проверяет JSON Schema, обязательные поля, ограничения размеров и форматов. Присваивает correlation ID, если он отсутствует; не меняет пользовательский смысл данных.

### Task Router + Task Registry
Сопоставляет task_type с конкретным обработчиком. Registry хранит:
- тип задачи;
- версию обработчика;
- требуемые capabilities;
- необходимость LLM;
- входную и выходную схемы;
- правила approval;
- quality checks.

Не разрешается выбирать инструмент по произвольной инструкции внутри пользовательского текста.

### Context Manager
Собирает только необходимые источники. Каждый фрагмент контекста должен иметь происхождение: источник, идентификатор/ссылка, время получения и тип. Инструкции из документов и внешних сообщений считаются недоверенными данными, не системными правилами.

Для RAG-задачи фиксируются retrieval query, возвращённые источники и релевантность по выбранному проверяемому порогу. Если обязательного источника нет — вернуть контролируемый результат insufficient_context, а не выдумывать ответ.

### Model Adapter
Изолирует API-провайдера от бизнес-логики. В V1 — один GigaChat adapter для сценариев, действительно требующих генерации или классификации:
- единый внутренний формат messages;
- таймаут и ограниченный retry только для безопасных запросов;
- нормализация ошибок авторизации, лимитов, недоступности и некорректного ответа;
- лимиты на входной и выходной объём;
- метаданные модели и фактическая стоимость, если провайдер отдаёт надёжные данные.

Модель не получает право выбирать инструменты или обходить разрешения. Вызов модели сам по себе не запускает внешний side effect.

### Tool Gateway
Все внешние действия вызываются через реестр инструментов. Перед вызовом проверяются:
1. capability зарегистрирована;
2. capability разрешена для данного task_type;
3. capability присутствует в разрешениях конкретной задачи;
4. аргументы прошли схему;
5. политика approval выполнена;
6. operation/idempotency key ещё не завершён или не находится в неоднозначном состоянии.

Разделять инструменты по реальному эффекту. Например, отправка черновика владельцу, передача копируемого текста владельцу и прямая публикация в канал — три разных capability.

### Quality Gate
Детерминированные проверки:
- структура и типы результата;
- наличие обязательных полей;
- допустимый статус;
- совпадение выходного task_id;
- наличие источников, если задача требует подтверждённых фактов;
- отсутствие незапрошенных side effects;
- длина/формат сообщения по требованиям канала.

LLM-as-judge не является обязательным критерием V1 и не заменяет эти проверки.

### Approval Manager
Формирует неизменяемое описание действия, получателя, канала, содержимого/параметров, задачи и operation key. Решение связывается с конкретным approval ID и конкретной версией действия. После изменения содержимого старое согласование становится недействительным.

Нужны действия approve / reject / expire. В V1 Telegram может быть интерфейсом подтверждения, но бизнес-решение не должно быть зашито только в Telegram callback.

### State + Audit Log
Хранит состояние задачи, попытки, переходы статусов, operation keys, результат и диагностические ошибки без секретов. Лог должен позволять восстановить «что произошло» без раскрытия payload, если он чувствительный.

Не вводить отдельную БД до доказанной потребности. Однако используемое хранилище должно поддерживать атомарную фиксацию состояния до внешнего действия. JSON + одна реплика допустимы как ограниченный V1-подход при наличии резервного копирования и ручного восстановления.

## 4. Контракт и статусы

Основной контракт определён в task-contract.schema.json.

Статусы:
- received — задача принята;
- running — обработка выполняется;
- waiting_approval — ожидается решение человека;
- completed — результат и все необходимые действия завершены;
- failed — задача завершилась ошибкой;
- cancelled — задача отменена.

Правила переходов:
- received → running | cancelled;
- running → waiting_approval | completed | failed | cancelled;
- waiting_approval → running | cancelled | failed;
- terminal states не меняются автоматически. Повторная попытка должна иметь зафиксированный номер попытки и тот же ключ логической операции, когда это безопасно.

Неоднозначный внешний side effect переводится в ручной разбор; он не должен автоматически превращаться в новый вызов.

## 5. Идемпотентность: важное ограничение

Exactly-once для внешнего API нельзя обещать только за счёт локального JSON-файла. Система должна обеспечивать безопасную обработку повторных событий и не повторять действие после неизвестного исхода.

Для внешнего действия:
1. создать уникальный operation key;
2. атомарно записать intent и статус dispatching до сетевого вызова;
3. выполнить вызов;
4. записать подтверждённый результат;
5. при timeout / потере соединения после отправки записать needs_review / unknown_outcome и не повторять автоматически.

Если провайдер поддерживает собственный idempotency key, использовать его. Если нет — требуется сверка/ручное решение. Отсутствие доказательства выполнения не означает, что действие не состоялось.

## 6. Политики для message automation

Базовая конфигурация V1:
- telegram.owner_draft.send — разрешить только предназначенному владельцу/чату;
- smmplanner.copy_handoff.send — разрешить после подтверждения владельца;
- social.publish.direct — запрещено по умолчанию, отдельное разрешение и отдельный тестовый канал обязательны;
- external.delete, financial.execute — не входят в профиль message automation.

Копируемый текст должен быть идентичен версии, которую человек согласовал. Любое изменение текста после approve требует нового approval.

## 7. Принципы хранения

V1:
- использовать существующее хранилище после проверки;
- не хранить API tokens в task envelope или audit log;
- не логировать полные персональные/клиентские payload без необходимости;
- закрепить однорепличный режим, пока нет общего lock/transaction store;
- тестировать восстановление после аварийного завершения.

## 8. Нефункциональные требования

- таймауты обязательны для всех сетевых вызовов;
- число повторов ограничено и зависит от класса операции;
- retry безопасен только для read-only или подтверждённо идемпотентных вызовов;
- секреты не попадают в логи и ошибки пользователю;
- все переходы статусов проверяемы;
- критические действия требуют approval;
- production конфигурация не меняется из тестовых workflow.
